# Security review and privilege matrix — 16 September 2026

Runbook §9's security gate asks for a completed threat-model review and a documented
privilege matrix. Until this file neither existed. This is the first of each, written from the
code as it stands at NERVIS 0.34.14, RAVIS 0.29.1, SIRVIS as shipped, and Clarvis 0.17.16. It is
a review, not a sign-off: the findings at the end are open until the owner decides on them.

**How it was made.** Every route of SIRVIS (38), RAVIS (93) and NERVIS (130) was listed by
building each application in a scratch folder and reading its route table — nothing served,
nothing called — together with the guard each route declares. The routes that accept writes
(SIRVIS 9, RAVIS 51, NERVIS 73) were then read one by one where the guard lives inside the
handler rather than in the route table. The Clarvis Bridge was read in `clarvis/src/bridge/`.
Anything below that names a file was read there on this date.

## The boundaries everything rests on

1. **This Mac's user account.** Every service runs as the owner, and every credential the
   launcher mints sits in `.run/` at mode `0600`. Any program the owner runs can read them.
   Nothing here tries to defend against the owner's own programs, and saying otherwise would be
   false: a process that can read `.run/` or the dashboard page can do what they can.
2. **Loopback only.** SIRVIS, RAVIS and NERVIS refuse to start on any other address
   (`_check_remote_exposure` in each `config.py`); the Clarvis Bridge binds `127.0.0.1` and an
   OS-chosen port (`clarvis/src/bridge/server.ts`). Another machine reaches nothing. Remote
   access with TLS and authentication is not built (runbook §9).
3. **Browsers.** A web page on another site can make the owner's browser send requests to
   `127.0.0.1`. Each service refuses those before reading them: a `Host` allowlist against DNS
   rebinding, and an origin check on every write (`nervis/src/nervis/api/origin_guard.py`;
   RAVIS's `check_host`, `check_origin` and `check_content_type` in `ravis/src/ravis/app.py`;
   SIRVIS's host check in its middleware, `sirvis/src/sirvis/app.py`, and its origin check in `require`, `sirvis/src/sirvis/api/security.py`, which every write passes). A write carrying neither
   `Sec-Fetch-Site` nor `Origin` is not a browser's and is let through to the service's own
   checks — which for NERVIS means boundary 1 is the only one left.
4. **Credentials between services.** Each service decides for itself; a caller's claim is
   never a grant (runbook §9, "the owner enforces permission").

## Privilege matrix

Who can do what, as built. "Local program" means any program running as the owner.

| Who | Holds | Can | Cannot |
|---|---|---|---|
| **The owner, at the launcher or menu bar** | every file in `.run/`, including `admin.owner_cli` | start and stop the stack; sign Codex in; stop a Codex task; re-test Codex's file rules (`POST /api/v1/codex/reprove`, the only route that takes `admin.owner_cli` alone) | — |
| **The dashboard page** (NERVIS's own origin) | SIRVIS `read runtime` token (in the URL fragment); NERVIS's per-process control token (in the page) | read everything; load and unload models in SIRVIS; through NERVIS: change RAVIS's configuration and credentials, Codex sign-in, sites and skills, NERVIS settings, workspace edits, the Code tab's session (control token); attachments, chat, notifications, voice, supervision, settings import (origin check only) | hold any RAVIS credential, SIRVIS's `benchmark` or `admin` token, or a provider key — NERVIS keeps those |
| **NERVIS** | RAVIS `admin.launcher` and `client.nervis`; SIRVIS `benchmark` and `admin` tokens; the enrollment secret; each Bridge's token; the Fish Audio key | proxy an allowlisted set of RAVIS and SIRVIS reads (`BY_KEY`; unknown surfaces are 404); carry out the enumerated operations in `nervis/src/nervis/commands.py` and publish each attempt; queue benchmarks; delete a benchmark result; start, stop or restart a service registered as NERVIS-managed with a configured adapter, once supervision is switched on | read a peer's database; forward a free-form request to a peer; change the upstream of the `/code/` proxy; approve a Clarvis gate; re-test Codex's file rules (RAVIS refuses `admin.launcher` there) |
| **RAVIS** | provider keys (keyring or file store); its Codex home | call providers; run and supervise Codex; decide routes | be told a caller's identity by header — identity comes only from a stored `client.` or `admin.` credential (`ravis/src/ravis/identity.py`) |
| **A RAVIS `admin.` caller** | an `admin.` credential | everything a client can, plus credential and configuration writes, Codex sign-in, version acceptance, site removal, skill changes; a Codex owner Stop, for the applications RAVIS lists for it (`require_owner_stop_caller`) | the file-rules re-test (`admin.owner_cli` only); agent-session routes |
| **A RAVIS `client.` caller** (NERVIS, Clarvis) | a `client.` credential | model calls at 600 a minute; the applications RAVIS lists as agent clients (Clarvis): agent sessions, project locks, adding a site — never with an `admin.` credential (`require_agent_client`) | credential or configuration writes |
| **An anonymous RAVIS caller** | nothing | model calls and reads at 60 a minute | any management write |
| **A SIRVIS caller by scope** | a token with `read`, `benchmark`, `runtime` or `admin` (`sirvis/src/sirvis/api/security.py`) | reads are open; `runtime` opens and closes sessions it owns; `benchmark` queues and cancels jobs; `admin` downloads and deletes results — and implies every other scope | end another caller's session (`_require_lease_owner`) |
| **Clarvis, in VS Code or code-server** | `client.clarvis` from `CLARVIS_RAVIS_CREDENTIAL` (code-server's environment) or its own stored key; the Bridge token NERVIS issued | model calls; Codex tasks through RAVIS; its own tool calls, each through its own approval gates | be steered by text inside files, command output or diagnostics — fenced as data since Clarvis 0.17.16 (`clarvis/src/agent/toolFence.ts`) |
| **The Clarvis Bridge** | the token NERVIS issued at registration | answer NERVIS's reads: health, identity, capabilities, version, status, config and the event stream — `GET` only, any other method refused before the path is read, and every read refused without the token, so nothing is served before registration (`server.ts`) | take any instruction from NERVIS |
| **Codex** (through RAVIS) | RAVIS's Codex home, the owner's ChatGPT plan | work inside one task folder under the pinned, calibrated file rules; reach the sites allowed for that task | reach the ecosystem's own repositories (refused by RAVIS); answer its own approval requests |
| **A model's output** | nothing | be shown, be proposed as an action for a person to confirm | become an action: there is no path from model output to `commands.run` or a gate |
| **A local program** | whatever the owner's account can read | anything the owner can, including everything above | — (boundary 1) |
| **A web page on another site** | the owner's browser | send requests that each service refuses unread (boundary 3) | read any response; learn NERVIS's control token |
| **Another machine** | network access | nothing — no service listens beyond loopback | — |

## Threats considered

| Threat | Stopped by | Status |
|---|---|---|
| A website drives the stack through the owner's browser | Host allowlist and origin checks in all three services; the Bridge answers `GET` only with a token | Held |
| DNS rebinding | Host allowlist, checked before anything reads the request | Held |
| Another machine on the network | Loopback-only binds, enforced at startup | Held |
| A leaked or guessed credential | Separate credentials per holder and per power (SIRVIS scopes, RAVIS `client.`/`admin.`/`admin.owner_cli`); timing-safe comparisons; nothing secret in URLs except the fragment, which never reaches a server | Held, with SIRVIS `admin` total by design |
| Text inside files, tool output or retrieved content steering an agent | Clarvis's fence (0.17.16); NERVIS's fenced diagnostic packet (§11.5); approvals ignore tool output | Held, not yet seen in a real run |
| A model's output triggering an action | Enumerated operations, confirmed by a person, no model on the path (`nervis/src/nervis/api/commands.py`) | Held |
| NERVIS used as an open relay | Allowlisted peer surfaces; the `/code/` upstream fixed by configuration (`nervis/src/nervis/api/code.py`) | Held |
| A forged settings file | Import accepts only the export allowlist (`EXPORTABLE`); no adapter, credential or path is importable | Held |
| Codex leaving its folder | Pinned build, calibrated file rules, protected repositories refused, per-task process tracking | Held for the calibrated build |
| A vulnerable dependency | `tools/check_dependencies.py` | Checked since today; five advisories left in Clarvis's build and test tools only |
| Secrets committed to git | `.gitignore` plus `tools/check_no_tracked_secrets.py` | Held for known file patterns; there is no content-based secret scan |
| A same-user program | Nothing, by design (boundary 1) | Accepted |

## Findings

**S1 — NERVIS's supervision routes skip the control token.** *Fixed the same evening in NERVIS
0.34.15: all four need the token, and `nervis/tests/test_control_token.py` lists them.* `POST /api/v1/supervision/adapter/{service}`
stores any executable file with any arguments as the way to start a service, and
`/supervision/enable` and `/supervision/{service}/{operation}` switch supervision on and run it.
They pass the origin check but not `require_control`, which NERVIS's RAVIS-changing routes
need. Reaching a start needs a service registered as NERVIS-managed, and registration needs the
enrollment secret; on 16 September supervision was switched on and every registered service was
external, so nothing could be started. The exposure is only to a caller that already passes
boundary 3, which today means a local program — no escalation. Still, the one route in NERVIS
that can name a program to run is the least guarded of its writes. *Recommended:* require the
control token on the four supervision writes, and consider limiting adapters to the ecosystem's
own console scripts.

**S2 — Other NERVIS writes skip the control token too.** The Fish Audio key
(`PUT`/`DELETE /api/v1/voice/credential`), settings import, recall and background switches,
chat and notification writes, and the learned-notes deletes pass the origin check only. The
control token's own module explains it defends the RAVIS writes one hop up; these never
reached that bar. The token adds defence in depth only — a caller who can read the page can
read the token — so this is consistency, not a hole. *Recommended:* add it at least to the
voice credential, which stores a provider key. *The voice credential was done in NERVIS 0.34.15,
and the rest on the owner's word in 0.34.17: one rule in NERVIS's request filter asks the token of
every write under `/api/v1/` except those in S7, and the page adds it to every write it sends, so
a route added later is covered without remembering to be.*

**S3 — Credentials are plain files readable by the owner's programs.** `.run/` at `0600`, and
`CLARVIS_RAVIS_CREDENTIAL` in code-server's environment, which its terminals and extensions can
read. Documented in `tools/run.py` and accepted: each is a loopback credential for a service
the same user controls.

**S4 — SIRVIS's `admin` implies every scope.** Documented in `security.py`; NERVIS holds that
token only for deleting benchmark results. Accepted.

**S5 — No content-based secret scan.** The gate checks tracked files against `.gitignore`
patterns, not their contents. A key pasted into a tracked file would not be caught.
*Recommended:* a content scan in the pre-commit hook, if wanted. *Added the same evening on the
owner's word: `tools/check_secret_content.py` checks every commit's added lines, and the
clean-clone gate every tracked line, for keys by shape and for this machine's own launcher and
enrollment secrets by value, naming the file and line and never the secret.*

**S7 — NERVIS's event delivery is open to any local program.** `POST /api/v1/events` is how
SIRVIS, RAVIS and each Clarvis Bridge report what happened, so it cannot ask for the page's
token, and it asks for nothing else. A local program can post events, which NERVIS stores,
shows and — since NERVIS 0.34.12 — may turn into notifications. Registration needs the
enrollment secret, and a registered Bridge's heartbeat and deregistration its own token.
*Possible fix:* have every producer present the enrollment secret on delivery. The exposure is
boundary 1's only.

**S6 — Remote access is not built** and nothing owns it (runbook §9). Not a hole while every
service refuses non-loopback binds.
