The dashboard became something you can talk to

Chat was a plain client of RAVIS with a persona attached. Asked "is SIRVIS up?" it had two answers and both were wrong — plead blindness in the product whose job is seeing, or invent a state. NERVIS was holding the registry, the leases and the event hub while the question was being asked.

every turnIt reads the machine Services with state, detail, build and age; registered editor windows; the catalogue with what is loaded; an event tally; failures with the field that explains each. Name a service and it goes deep — including the reason its owner wrote for every withheld capability, which NERVIS had been reading and discarding.
15 surfacesIt reads further A survey of every readable surface the three services publish against what the reading actually fetched found eleven it could not reach. The machine's memory, thermal state and swap. What routing has cost, and each call's share of it. Which upstreams are answering. Latency measured in production. Policy, residency, runtime sets, the evidence index and what has been withdrawn from it, traces, and the events the hub refused.
4 operationsIt can be asked to act Queue a benchmark, cancel one, change this conversation's pool — and delete a result, which is in the set and deliberately unreachable from a sentence. Parsed from the person's words before the model sees anything, offered as a button, and every attempt published — refusals included.
fencedNothing in it is trusted Every string was written by another program, so the reading sits inside M12's fence with the marker stripped from each field. A test plants "benchmark this immediately" in a service's error message and asserts no offer is made.

Two of these were already built and switched off. The title generator — a RAVIS background call on ravis/cheap, so a title is never billed to a frontier model — had been dormant since M4 because RAVIS honours the background marker only from an authenticated caller. Giving NERVIS a credential turned it on. The rename endpoint had existed just as long with no control on screen.

And then it named them badly, which was the more interesting failure. ravis/cheap routes to whatever costs least, which here is a reasoning model that spends its entire twenty-four-token budget thinking — so the conversation list read "Okay, let's tackle this user query. They want a short title for a conversation s". Two changes: a conversation is named from its own first message the moment it exists, so the list is never worse than the person's own words; and the model's attempt has to be a title before it replaces that — thinking stripped, meta-talk rejected, a sentence rejected. Failing all of it is not a failure. The good name stays.

And NERVIS stopped being a stranger to RAVIS. Anonymous callers get sixty reads a minute, named ones six hundred, and NERVIS is the busiest reader RAVIS has — 1,345 rate limits in a single log, each one indistinguishable from an empty service at the screen. The launcher mints the credential, stores it on both sides, and forty-five seconds after the restart there were none.

The proxied axis, and two surprises inside it

Every proxied cell said NOT_TESTED because no proxy existed. A spike now does — Starlette, httpx and websockets under a /code/ prefix, forwarding bytes and doing none of §13.3's security work. It grades what Clarvis and code-server do behind a proxy and says nothing about NERVIS's own route, which is still unbuilt.

observedIt all works Base path needs no rewriting: code-server emits relative URLs throughout. An 18.5 MB workbench bundle survives the hop byte-identical. Driven by the operator: workbench rendered, Clarvis panel answered, terminal opened — the WebSocket carrying traffic rather than merely upgrading.
surprise 1It worked because it was insecure The proxy forwarded Cookie and nothing else, so code-server never saw an Origin header — and its own source says of that case: “probably means the source is non-browser … let it through.” The check had not failed. It had not run.
provenNow it runs, and refuses Settled by falsification on a throwaway auth-none instance, so no password was involved: proxied with a matching origin connects, proxied with evil.example is refused 403. RFC 7239 Forwarded is what makes a legitimate origin match.
surprise 2The keychain came up empty Under code-server, secrets live in browser storage, which is partitioned by origin. Reaching the same editor by a different URL presents an empty keychain — nothing lost, the keys sit at the old origin. Two defects in the spike were found the same way: it answered outside its own prefix, and .. walked out of it.

The second surprise is the one with consequences. Moving the Code tab behind a NERVIS route would empty every user's keys on upgrade, while the old ones linger readable at the old origin. It is the strongest argument yet for RAVIS holding provider credentials: a Clarvis pointed at ravis/* keeps no provider key in the browser at all.

The read that exists so a write does not have to

Asked whether chat could change a Clarvis setting, the answer was no — and the specification says so at agents specifically. CLARVIS.md §6.7 forbids NERVIS changing a safety setting and closes with “an agent asked to add such control must stop.” The Bridge refuses every non-GET before it looks at the path; code-server has no settings-write API at all; the file on disk is reachable, and writing it would be invisible to Clarvis's own audit and would race the editor's in-memory copy.

builtThe useful half instead clarvis.config.summary@1 publishes what Clarvis is configured to do — the values in force, the setting id for each, and how to change it. Read live: chat.model ravis/clarvis-chat, chat.mode auto, theme clarvis-nervis.
the pointWhere the control is "Search for clarvis.chat.model in Settings" is the worst true answer. The route is authored in Clarvis beside the affordance: click the bowtie to the left of the prompt to open the models menu. Every command title in those routes is checked against the manifest.
allowlistWhat may leave the machine Model names, providers, modes, booleans, theme. Never a path — whether an enrolment secret is configured travels, the path does not. Never a URL somebody typed — a base URL becomes loopback, remote or unreadable.
twiceFiltered on both sides The Bridge publishes an allowlist and NERVIS repeats an allowlist. The Bridge's port is dynamic and anything on this machine can bind one, which is the same argument the status read already makes.

Verified against the open window, and the answer it produced: “Clarvis is using ravis/clarvis-chat… click the bowtie to the left of the prompt, or run Clarvis: Choose Model.” Clarvis's own sentence about its own panel, quoted through the Bridge.

The dashboard stopped inventing data

Every fabricated value is gone from all 35 screens. The mock fallbacks first, then the constants behind them: a bundled LM Studio snapshot, benchmark numbers taken on one machine on one evening, complete route decisions naming every candidate and why each was eliminated, a download queue, a catalogue with sizes, MEASURED evidence records. All plausible, all checkable, none of it asked of a service.

The PROTOTYPE badge went with them, because there was nothing left for it to apologise for. The fade stayed: a card with no data still reads as quiet rather than broken.

Emptying them exposed nine screens that assumed data always arrives. A route label read off two lookups that both return undefined, a failure explainer read off a failure that was not there, prose read a throughput field with no guard. Every one was reachable the moment a service went quiet. render_check draws all 35 screens with nothing running — exactly that path — so each surfaced in seconds.

The Clarvis conformance card was the sharpest catch, and it came through no mock at all: ten green pass ticks rendered from a constant, under a chip reading shape, not a run. Nothing had run, and no result is readable from a browser — it is a CLI command, and the endpoint answers 404. The check names stay; the verdicts are gone.

Injection sites fell from 22 to 9 as a side effect, since the deleted fixtures took their template literals with them — and the ratchet was lowered to 9, which the gate had been asking for in its own output. The liveness ratchet sits at 51 hardcoded against 58 deriving, set from the finished state rather than mid-sweep.

Clarvis is now the editor, embedded

The Clarvis tab is code-server itself, not a drawing of one: an iframe at 127.0.0.1:8080, laid out oversized and scaled to .85 so the workbench sits at the dashboard's density. The launcher starts and stops it alongside the three services, and it appears on the ecosystem map as CLARVIS.

The theme ships with the extension — clarvis-nervis, 88 workbench colours and 15 token rules — rather than living in one machine's settings file. Selecting it by its label silently resolved to nothing and fell back to the default light theme, so a test now requires the id be plain ASCII and differ from the label.

And the tab now refuses hosts nobody graded. This was Stage 9's other exit clause — unsupported combinations are blocked in the UI — and it had nothing behind it for the whole spike. NERVIS had been reading code-server's version off its login page since the beginning and doing nothing with the number, which is the quiet kind of gap: a version printed on a screen reads as a check that was made.

Three answers rather than two, because the two cases are not alike. The graded 4.135.0 embeds. Anything older is refused outright and no frame is drawn — nothing was ever run against it, and an untested editor that looks like a working one is the whole failure being prevented. Anything newer, or a version whose page could not be read, embeds behind a banner saying which. A hard allowlist of the single graded version would take the editor away the first time somebody upgrades code-server, which punishes the user for a gap in NERVIS's testing rather than a fault in theirs.

The gate is a capability, not a field invented for the screen, so blocking reads the same mechanism every other capability does and carries §4.1's mandatory reason — blocked without why is indistinguishable from broken. And it was settled by falsification, not by watching the version that already passes: a fake code-server answering the three paths the adapter reads, and a second NERVIS with its own database pointed at it. 4.100.0 came back unavailable, 4.200.0 degraded, the real 4.135.0 available.

The Bridge earns its keep through one consumer. A window waiting on a gate raises an attention signal on the dashboard. The event stream is served, heartbeats, replays a backlog and carries the §6.4 families — and is read by nobody, so it advertises itself degraded rather than available.

Known partials, stated rather than hidden

Two of the twelve gate scripts are not in CI, deliberately: honesty_check and recovery_check both render every screen twice — once with every read failing, once against running services — so they say nothing useful with nothing up. They are checks you run, not gates that block a commit.

A route decision still cannot be addressed. §25 asks for it; the Routes screen renders decisions[0] and its rows carry no click handler, so there is no selection to link to. That is a screen change, not a router change.

Targeted updates landed as preserve-and-restore, not a keyed diff. The content region is still replaced wholesale on every render — what changed is that doing so no longer costs the reader their typing, caret, disclosures or scroll.

A runtime-set benchmark records no trace, so only the single-model path is externally visible. And SIRVIS's per-test events were considered and dropped: retention is count-bounded, so a chatty producer evicts its own opening event.

The Bridge advertises one capability, degrades one and withholds three, each with a reason rather than a silence. clarvis.events@1 is degraded because nothing subscribes; clarvis.diagnostics.summary is not built; clarvis.logs.reference waits on an approval step, because Clarvis's log deliberately records full command strings and sensitive paths; clarvis.ravis_provider is false because the model layer speaks to providers directly. A sixth, clarvis.voice@1, resolves per host — available on a desktop, degraded on a remote one.

Neither mode nor route reaches the dashboard, though CLARVIS §6.3 lists both. They read unknown in the instances card rather than blank, because a blank cell reads as a value.

Software nobody installed reported as a fault. Ollama has never been on this machine and NERVIS warned about it every time it looked — the registry entry already knew (awaiting_first_contact is §5.1's distinction) and only the browser banner read it. Memory outranked measurement, twice, before anybody noticed. The recall now says it is memory rather than measurement, and the reading is assembled after it. Position decided more of this than instruction did.

The status gate could not see its own drift. It checked the total test count and not the per-package ones, so an editing session that kept the total right while moving numbers between lines left three wrong figures in the file whose entire job is being believed. It checks each package now.

The pools meant nothing, and one of them was answering you

ravis/chat had 549 members, no requirement and no preference. The routing engine states the consequence in its own comment — "pools that say nothing fall back to alphabetical order, which is meaningless" — so ordinary conversation on this machine was served by amazon/nova-2-lite-v1, which won on the letter A. The size tiebreak compounded it: a model whose name carries a parameter count sorts ahead of every frontier model whose name does not, so a 1B instruct outranked gpt-5 because "1b" parses and "gpt-5" does not.

every poolDeclares what it draws from Conversational families for chat, code families for coding, models built to reason rather than models that merely accept the parameter. A claim about what a model is for, never about how good it is — ranking inside the class stays unmeasured and says so.
cost firstExpensive is a last resort The cheap-capable tier leads and the expensive tier is last — in the list, so it answers when nothing above it is available, and never what an ordinary turn reaches for. Chat picked claude-fable-5 for exactly one commit.
every poolA routable baseline ravis/auto held 41 image and moderation models; ravis/local held an embedding model. None can answer a chat completion. The knowledge existed — membership had never consulted it.
232 vs 295Two agent pools, finally distinct ravis/agent and ravis/clarvis-agent were member-for-member identical. §5.1 asks the Clarvis one for structured calls and long context as well, so now it requires them.

Curation stores nothing, and that is the whole design. The first version wrote each pool's computed membership in as a saved selection — which is the one change that would break it. A stored list is a snapshot of a catalogue that moves: this machine carried one of 549 models, saved when 549 was the catalogue and stale by 42 within a fortnight, while the screen reported it as the membership and the router used it. So the control removes pins instead, and membership is computed per request. A model a provider ships next week joins on its own.

And a script proposes, without ever routing. tools/propose_pools.py sends the 591-model catalogue to a model and asks which belong where. Every suggested fragment is checked against the real catalogue and the ones matching nothing are printed rather than dropped — "it invented four of these" being the most useful thing to know about a proposal. It writes a file. Applying it is a person's edit, because §11.5 makes a model's opinion retrieved content.

Evidence gained a way to be wrong about itself

Two things about SIRVIS's identity turned out to be broken in the same direction, and both were found by benchmarking one model twice.

Fixed
The runtime describes the wrong build

LM Studio groups several builds under one entry and its HTTP API reports whichever the app has selected, not the one that is loaded. It compounds it: a completion addressed to …@q4_k_m is answered while the metadata route returns "not found" for the same key — the runtime will measure a build it refuses to describe. And a non-selected variant is not published at all unless it happens to be loaded. This is not cosmetic: the MLX and GGUF builds of one gemma reach 24/24 and 21/24 on the same tool-call trial, and RAVIS admits and excludes on that. SIRVIS now asks the runtime's own CLI, refuses to record evidence it cannot attribute, and enumerates installed builds additively — and only for a loopback runtime, since the CLI reads this machine's disk.

Fixed
Two builds collapsed into one record

The installed map was keyed on the family, so the resident MLX and the GGUF folded together and the first writer won. The machine held two builds and reported one — the Models screen showed MLX and no GGUF, and a benchmark of the invisible build had no identity to file under.

Built
A result can be deleted, and says so afterwards

The evidence surface published tombstones: [] since M16 under a comment saying nothing deleted a result and whoever added retention would have to fill it. DELETE /benchmark-results/{id} is that — admin-scoped, because a client trusted to spend an hour of machine time is not thereby trusted to erase what that hour produced. What survives is the tombstone: a build with no evidence and a build whose evidence was withdrawn are indistinguishable on every other surface, and lead to different decisions.

Three ways chat was silent about things it had

Asked how the GGUF gemma did on tool calls, chat answered from the two most recent results on a machine holding eighty-seven. Correct, current, and about something else entirely. The cause was three gates stacked, none visible from the code that looked wrong.

gate 1Results rode on the queue They were fetched only if the job queue read had returned something — and that read triggers on "bench", "job" or "queue". A finished measurement outlives the job that produced it and is asked about in neither word.
gate 2Three read, two printed Always the newest. The run being asked about sat fifteen deep. The window now widens when a question names a build, and matching runs are selected ahead of recent ones.
gate 3Trial rates were invisible They are counted rather than averaged, so they carry no median and the metric reader skipped them without a word. A question about tool calls was answered from throughput and latency.
andSUSPECT had no reason Validity is literally SUSPECT if warnings else VALID and the notes are those warnings — so quoting two of three left chat able to state the verdict and unable to justify it.

The last one needed a second fix nobody would have predicted. Two runs of one build produced blocks identical character for character, differing only in the reasons underneath — and asked to explain them, the model attributed one block's swap warning to the other's build. Nothing in the reading could have told them apart. Each result now says when it ran.

Stage 9's matrix is fully graded, and running it found the bugs

Eleven cells were untested that morning and none are now. What the day actually produced was not eleven confirmations — it was two defects in Clarvis, one fixed FAIL, and two cells that needed an instrument the obvious method could not supply. Reading the code had graded every one of these correctly; running it found what reading could not.

found by runningThe task double-count The cell predicted it: a naming detail "a browser-hosted terminal could order differently". It does. One task run produced two outcomes 3 ms apart, because the guard identifies a task's terminal by its name being empty and code-server names it immediately.
found by runningA peak meter reading a version string peakDbfs skipped a fixed 44 bytes; ffmpeg writes a LIST chunk first, so samples start at byte 78 and the text Lavf62.12.102 read as int16 peaks at −1.9 dBFS — identical on every run. hasAudio therefore said yes to any clip, including one from a denied microphone.
fixedAudio on a split host Tier 1 sends rendered audio to the webview where the workbench is a browser or the host is remote. Most of that path already existed and had never been used: the webview's speak-audio handler and the panel's media-src data: were both there. The sender was missing.
asked, then builtCapture, the same bug inverted Recording spawned ffmpeg on the extension host, so it took the server's microphone. Whether the panel could record instead was not assumed: a webview is a cross-origin iframe and getUserMedia needs a permission the workbench grants, which Firefox will not report. Five lines of probe asked; the answer justified the route.
attributedReaching LM Studio A request in LM Studio's log proves nothing here — SIRVIS polls it every twenty seconds. What attributes it is Clarvis's log carrying LM Studio's own error text back, so the extension host reached the port itself.

The mic probe is the one worth dwelling on. It reported success — and it was the diagnostic built precisely because a denied microphone exits 0 with a well-formed file. Measuring the wrong bytes made it answer "captured audio" for exactly the failure it exists to detect. The unit tests missed it because their fixture built a header from forty-four zero bytes: no chunk structure to get wrong, nothing to contribute to a peak. A fixture easier than the real thing tests something easier than the real thing.

The audio defects turned out to be one bug written twice. Playback assumed the extension host was the listener; capture assumed it was the speaker. Both are fixed the same way — through the panel — and both were confirmed from outside the system that reported them: speech heard from the browser, and a recording whose sample rate, size and measured level all say it came from somewhere the old path could not have produced.

One design choice is worth naming, because the cheap option would have undone the morning's work. MediaRecorder is far less code and produces Opus, which peakDbfs cannot read — and that check is the only thing separating recorded audio from recorded silence from a denied device. It had been broken until hours earlier. So the webview builds a WAV instead, and the clip goes through exactly the same analysis as the host path: what changes is the microphone, not the measurement.

And one capability had to be rewritten because the code stopped being true. clarvis.voice@1 advertised itself as degraded because "speech plays on the machine running the extension host". After the audio fix that sentence was false, and a capability describing yesterday's defect is worse than one saying nothing, because a peer acts on it. It stays degraded for the smaller true reason — the panel must be open and clicked once, since browsers refuse audio before a gesture.

The three open failures turned out to be none. Two had been fixed the day before and each cell body said so; only the headings and the count above them were never changed, so the matrix reported failures it did not have. The third was settled two cells further down. Nothing was fixed today — the ledger was wrong, and a ledger that overstates what is broken costs the same attention as one that hides it.

So the tally is now computed from the cell headings rather than typed. The number and the cells can no longer disagree, which is the only durable fix: the stale count was not an oversight anyone would catch by reading, because the page it lived on looked internally consistent.

Clarvis also stopped calling every build 0.0.1. It is 0.9.0 now — pre-1.0 because it is not released, .9 because the ladder has one stage left. The build stamp carries the version and a timestamp rather than a timestamp alone, because they answer different questions: which build this is, and whether the extension host is running it yet. That second question is not academic — installing a .vsix replaces the file on disk while the host keeps the old bundle in memory, which is exactly how a CSS fix was reported done while the panel still showed the old layout.

Speech input now has a route and no feature behind it. The capture path exists because the probe needed it, and the probe is its only caller: there is no speech-to-text anywhere in Clarvis. That is worth stating rather than quietly building towards — the route was worth opening because it settled a matrix cell, and dictation is a product decision nobody has made.

Stage 10 is now the ladder's front, and the day is a warning about how it will feel. Two stages closed, and both closed on clauses that a finished-looking artefact had stopped mentioning: three failures that were already fixed, and an exit clause the completed matrix concealed. Hardening is nine categories of exactly that shape — acceptance, degradation, security, load, long-running, upgrade, downgrade, backup, rollback — and the failure mode is not missing work, it is work that looks done.

NERVIS M11, the API inspector, remains the strongest piece of NERVIS-side work and needs nothing from Clarvis. Route decisions carry an explanation, RAVIS publishes selection and completion events under the caller's trace, and the trace assembles into spans — M11 turns material already being produced into the one screen that answers “what happened to this request”. Chat can now narrate that record in prose; the screen is where it becomes navigable.

Or widen the operation set, carefully. Four operations exist now, and the fourth set a precedent worth keeping: deleting a result is in the closed set and has no phrase that reaches it, because a measurement is not a thing to offer to destroy on the strength of a parse. The constraint that made the first three defensible still holds — an operation NERVIS cannot resolve to a specific target is not offered, and nothing a model returns may become one. The next candidates are load and release through SIRVIS's Resource Manager, which already owns them and already refuses anyone without the right scope.

And the pools now have a shape worth measuring against. Every one declares what it draws from, which is a judgement made by hand against a catalogue that turns over every few weeks — defensible, stated as a preference rather than a measurement, and exactly the kind of thing §13's evidence is supposed to replace. Deriving pool membership from role evidence rather than from declared families is the honest end state, and the tool-call trials are already the first axis that could do it.
